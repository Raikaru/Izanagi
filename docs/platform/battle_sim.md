# Native battle simulator

This is a port testing tool, not a gameplay mod. Implementation/qualification is phased: (1) save-backed entry and one completed same-input deterministic battle, (2) the three observation-limited party policies and admitted parallel seed batches/reports, (3) retained PS2 witnesses through the existing lockstep harness. A phase is accepted only with its exercised evidence; the contract below is not evidence of implemented or qualified behavior.

## Worker contract (schema 1)

The coordinator invokes `p4pc[64|64w] ELF --battle-sim ENTRY --battle-result RESULT --battle-trace TRACE`. `ENTRY` is an immutable, bounded binary compilation of scenario JSON: a checked native engine save image plus typed control records, not executable code or an arbitrary guest-address/write interface. The native save remains engine-owned serialization; no host paths or host pointers are added to it. `RESULT` and `TRACE` must be new files in the coordinator's private run directory. The battle-run worker never opens a source card for writing or exports its mutated fight state; only the separate explicit preparation command exports a typed, validated effective image. Competing automation/mod/override environments are refused. Ordinary launches without a battle-tool option retain their existing behavior.

The ordinary-game mod-test exception is never a fidelity exception: **presence** of `P4PC_MOD_WITNESS`, including an empty value, is rejected before source reads/output. The coordinator also refuses it before inherited-environment sanitization; dropping/resetting a witness marker must not promote a run into simulator or retail-comparison evidence. Native battle preparation follows the same fence. The one exception is a scenario's declared mod cohort (below), which the coordinator itself runs as an explicit, non-reference mod-witness batch.

The ordinary-game mod-test exception is never a fidelity exception: **presence** of `P4PC_MOD_WITNESS`, including an empty value, is rejected before the worker reads ENTRY or creates output. It may not be stripped/reset and promoted into a simulator or retail-comparison run.

All integer fields and array words are little-endian unsigned32, except explicitly signed native bit patterns. Header is exactly64 bytes:

| Offset | Field |
| --- | --- |
| 0 | eight ASCII bytes `P4BSIM01` |
| 8 | header size,64 |
| 12 | flags: bit0 renderless; bit1 captured-RNG replay; bit2 explicitly fill initial living party HP/SP; all other bits rejected |
| 16 | native encounter ID (0..65535; bound again against loaded encounter resource) |
| 20 | additive RNG seed bit pattern |
| 24 | MT RNG seed bit pattern |
| 28 | completed-update limit after launch, positive |
| 32 | input tape record count; for policy4 the walk plan's byte count |
| 36 | exact native save-image byte count, including its4-byte version |
| 40 | captured RNG byte count (0 in seeded mode;2648 in replay mode) |
| 44 | bootstrap update limit, positive |
| 48 | party policy:0 exact controller tape;1 greedy;2 cautious;3 typical;4 walk battle plan;5 attentive;6 attentive with Persona ratings;7 technical;8 strategic candidate |
| 52 | policy decision latency in completed native updates |
| 56 | policy action limit, positive |
| 60 | shared effect RNG seed bit pattern |

Following the header: checked native save image, optional RNG image, then the controller tape. Save layout/checksums follow the production NTSC-U importer and native `datSaveVerifyChecksum`/`datSaveRestoreImage`; restoration passes `file+4`, not a guessed tagged-data base. Before native restoration, require the complete canonical section order and exact byte counts shared with`lockstep_save_sections.inc`; the native compact variant may omit field sections37/38/39 only together. Checksum-valid partial images and incorrect native copy lengths are rejected rather than silently inheriting default state. Source/provenance and SHA-256 hashes are retained in the coordinator manifest rather than embedded host paths.
Each tape record is12 bytes: `(relative_update, button_mask, hold_updates)`. Updates are measured from the pre-construction entry boundary; no render/flip count is substituted. Button masks use native DualShock2 bits. Records must be sorted, nonoverlapping and bounded by the declared update limit; no keyboard/controller sampling is allowed. For tape policy0, exact replay includes latency and auxiliary Help/All-Out/result decisions and must not synthesize Cross input absent from the tape. Named policies reject nonempty tapes and own their explicit versioned decision/auxiliary-confirmation schedule in both rendered-reference and renderless workers; forced/scripted action ownership remains native.
RNG image:31 additive state words (124 bytes), front/back **word offsets** (8 bytes),624 MT state words (2496 bytes), MT index (4 bytes), shared effect RNG4 words (16 bytes), total2648. Word offsets must be within0..30 and maintain the real lag3 ring. The initial parser accepts MT indices0..623; the actual MT draw boundary still needs source/witness qualification before general captured-state replay is accepted. Native engine owns/binds storage; no pointers are serialized. Seeded mode calls real `RpRandomSeed`, `RpRandomSeedMT` and `effMiscRandInit(NULL, seed)` before encounter construction, not at COMMAND. Replay restores captured state instead and must qualify scheduler/context prerequisites; it is not arbitrary process-state restoration. Effect RNG (`004bd050`, seeder`004bd130`, shared bank`00922de0`) also drives camera consumers; preserve its draws and distinguish non-NULL private instances.
The initial`rng.draws` result field and`rng_draws` trace field count the instrumented **additive** stream only (`p4pc_rng_draws`), relative to the post-seeding entry boundary. They are not total draws across MT/shared-effect/private streams. Their full global state snapshots/hashes remain separate from any unimplemented per-stream call counters.
The worker emits JSONL state/event observations to TRACE and exclusive JSON to RESULT, finalized and checked before exit. Result outcomes distinguish `win`, `defeat`, `escape`, `scripted_conclusion`, `update_limit`, `action_limit`, `engine_error`, `policy_error`. Limits are censored, not wipes. Errors never become alternate successful seeds. A zero exit means a fully recorded native terminal outcome; a limit or runtime error is nonzero and still retains a result when publication is possible. Identity, state/RNG snapshots and counters must be qualified with actual runs before a batch report calls them fidelity evidence.

`resources.initial_party_boundary` is `after_restore_before_constructor`: `initial_party` is the restored/prepared persistent record, **not** an assertion about first COMMAND or the first committed turn. Cohorts must identify their requested/effective resource boundary and whether they inherit native current HP/SP or explicitly request preparation. Preserve native over-maximum current values in inherit mode; do not silently fill, clamp, reject or label the source unattainable because current resources exceed computed maxima. Report later native resource transitions separately from actual skill costs, damage and recovery.

## Natural-walk worker entry (schema 1)

`p4pc[64|64w] ELF --battle-sim ENTRY --battle-live --battle-result RESULT --battle-trace TRACE` selects a separate natural mode before any entry read. `ENTRY` is exactly64 little-endian bytes: magic `P4BLIVE1` at0, size64 at8; flags at12 (bit0 no-device, bit1 flip-clock walk); request mode at16 (1 script-sequence, 2 scripted-field, 4 ordinary field-collision pre-constructor); encounter u16 at20; positive matching occurrence at24; positive whole-route, selected-fight and action update bounds at28/32/36; completion scope at40 (1 fight-only, 2 walk and endpoint); endpoint mask at44 (bits1/2/4/8 select field/room/date/step) and those four u32 values at48/52/56/60. All other flag/mask bits fail. Fight-only requires a zero endpoint mask; walk completion requires a nonzero mask. Unmasked endpoint values must be zero. Occurrence counts matches of the declared mode and encounter ID, not unrelated prefix fights. An unobserved selector is not synthesized.

The controller stages a pristine full folder card under private `P4PC_SAVE_DIR/mc0`, and owns the ordinary title LOAD, real walker and lockstep packet hook. Live mode does not restore a save image, inject input, invoke the harness constructor, reseed/restore RNG, change tactics or replace the pad clock. It requires script input, mods/packs0, virtual clock1 and turbo2. Without replay it requires an explicit walk, `P4PC_AUTOPRESS_LOAD=0`, `P4PC_AUTOPRESS_FRAMES=1`, and walk clock matching the flag; flip-clock requires `P4PC_WALK_GAME` absent, not set to `0`. With lockstep replay, walk and LOAD automation are absent and the existing complete packet stream owns input. A full-route replay requires an explicit lockstep STOP and ends as a censored prefix, because a tape does not drive a live walker to DONE. Witness presence and competing battle/override automation fail closed. A no-device entry is not a framebuffer witness; GPU captures need a rendered entry.

Request capture stores the exact guest RAM range `0x00100000..0x01ffffff` as an exclusive `TRACE.request-ram` file only after the selected request is identified; its SHA-256 and boundary flip/game-frame are in TRACE and RESULT. Script BEGIN takes the pending copy before the original fade/getter, then IDENTIFIED selects it using the original getter result; field BEGIN copies before mutation/allocation. Ordinary collision mode 4 snapshots at `00172e00` case10 immediately before the native constructor, after the actual field collision, advantage RNG and scene transition; it must not be labelled an initial-collision snapshot. Request, task-begin, task-created, selected-fight terminal and route-final RNG observations retain the full additive31/MT624/effect4 words, active slot and **byte** cursor offsets. The dump does not include host scheduler or MMIO state. Task binding requires exactly one outstanding observed request, the actual group emitted by that request and a setup packet whose enemy group is the same pointer and has the selected native encounter ID. Both field modes check the original field task, actor, group and work packet address (`work+0x50`). Intervening requests or ambiguous/unbound constructors fail rather than binding a different battle.

The selected native terminal is retained before teardown. Per-update trace records bounded linked party/enemy unit identities, HP/SP and status, with the terminal linked-unit snapshot also in RESULT; an absent unit or absent record is not proof of zero HP. Fight-only exits with the real win/defeat/escape/scripted conclusion; walk scope continues normal cleanup until actual `P4WALK_DONE` and the declared endpoint predicates, keeping terminal and final-route RNG separate. A lockstep battle qualification (`P4PC_LOCKSTEP_BATTLE_ANCHOR`) ends at the same terminal update and labels its presentation: `fight_terminal.presentation` is `"presented"` when that update's own RASTERSHOWRASTER (which runs inside the update) advanced the flip count to `fight_terminal.flip`, `"unpresented"` when it drew nothing, and null outside qualification. `route_complete` does not by itself assert an actual save unless the source route/controller also verifies it. A lockstep STOP, clean replay EOF or accepted aligned boundary stop, including before the selected request, writes an explicitly labelled `observation_prefix`, not a victory or route completion; result publication failure changes that exit to nonzero while preserving the existing `port.complete` and replay-error ordering. Each primary, replay and mark capture needs unique RESULT/TRACE paths; the controller retains executable, entry, card, ELF, walk and input tape hashes independently.

This source contract is not a live-run or PS2 parity receipt. No natural entry is qualified until its actual task binding, complete fight, input/RNG observations and retail comparison are exercised.

### Selector-free natural discovery

The same `P4BLIVE1` entry accepts mode 3 solely for discovery: offset20 must be zero and offset24 is instead a positive **absolute flip ceiling**, not a selected ID or occurrence. Completion must be walk-and-endpoint (2), and the route-update, per-fight and action bounds and endpoint predicates remain mandatory. An actual DONE and matching endpoint at exactly the ceiling is accepted; otherwise reaching the ceiling fails with `update_limit` / `absolute_flip_limit` before any further update. The presentation owner also checks before beginning a further flip, so multiple flips in one update cannot pass the ceiling. The result records the ceiling, final absolute flip and guest game frame. The ceiling is independent of completed-update count and wall time. Replay is refused. The native walker, title LOAD, input, mods-off and clock requirements above still apply. Discovery subscribes to the natural event broker; it does not start a synthetic fight, alter RNG or party state, or inject pad input. It allocates no request-RAM snapshot and makes no RNG/retail equivalence claim.

The exclusive TRACE JSONL records each supported script and scripted-field request and each ordinary field-collision pre-constructor boundary in global order, actual mode and ID, per-(mode, ID) occurrence, native flip/frame and field/room/date/step, the group and exact constructor/task binding, each first protagonist COMMAND with linked unit/record identities and resources, and native fight terminals. A script BEGIN has null ID until the original getter identifies it; mode 4 begins only at the later collision pre-constructor seam, not the initial collision. Field group binding checks the original field task, work, actor and enemy-group pointers; all three modes require the setup's enemy group to match the observed group. An unbound constructor or an active battle without an observed supported request is an error, not a guessed selector. Ambiguous requests, missing witness or walk completion, failed endpoint, trace overflow or write failure also fail. The trace is capped at 8192 records and 8 MiB; result publication is exclusive and reports `entry_kind: live-discovery`, outcome, request/fight/command counts and any verified endpoint. A route-complete result still does not verify a save: the controller must inspect it independently.

The controller records executable, entry, complete source card and walk hashes, keeps the entire discovery event stream, and identifies a target only from its actual task/linked-unit and route-time evidence. A zero exit alone does not identify a fight, and no emitted supported request is not evidence that an uninstrumented collision path cannot exist. Discovery, like the selected worker, requires actual acceptance and a real run before any event is a witness.

### Fork search for a boss-win tape (Linux)

`P4PC_BATTLE_FORK=DIR` (Linux builds only; selected fight-only entries, not discovery, replay or aligned qualification) turns each fresh party command of the selected fight, once the walk's `battleturn:` lines are spent, into a checkpoint. The walker asks its host for the command's line (`P4WalkHost.battle_turn`, set through `p4pc_pad_set_battle_turn_hook`); the checkpoint flushes the trace, lockstep input log and per-frame states, requires a single-threaded process, writes `DIR/NODE/checkpoint.json` (turn number, update/fight/action counters, additive draws, the ready party member's native ID as `actor`, the linked units, their DatUnit record words +0x00 and +0x10..+0x20 as `record_words` (+0x00 bit `0x200` guarding, +0x14 bits `0xC0000` Power/Mind Charge, +0x1C.. buff nibbles) and the open descriptors) and serves the FIFO `DIR/NODE/control`, which it holds open read-write: a write never lands while only a just-forked child's inherited read end is open, which the pipe would drop when the child closes it. `fork NAME LINE` forks a child that continues as node `NAME` with `LINE` as the command (a `NAME` whose directory exists is ignored); its PID or a `fork_failed` marker lands in `DIR/NAME`. `exit` ends the checkpoint. A child writes its own trace, result, `lockstep/` files and stdout/stderr under `DIR/NAME`, reads the disc through a private descriptor at the same offset (`vfs_fork_private`), and changes no guest state, RNG, input schedule or clock, so a path's segments concatenate to one run of the same tape. The root node is `DIR/root`, which the caller may create.

`tools/battle_tas.py` drives it inside the Linux container (`python3 tools/battle_tas.py --worker p4pc64 --elf ELF --iso ISO --card CARD --walk WALK --encounter ID --out OUT`): the root runs the boss walk's own prefix, through `--prefix-through` (default `skiptask:battle`) or its first `--prefix-lines`, and then one `battle:` line (`--driver`, default a Guard fallback plan and `delay=80`, kept identical in search and gate). It offers Attack, Guard, the acting persona's listed skills it can pay for (none while silenced, ailment `0x8`) and the listed battle consumables still in stock (the walker's `battle_list` rules over the request-time RAM image), with `enemy:`/`ally:`/`dead:` bindings. A unit with no HP or with the knock-out ailment `0x80000` is down: never a target (the walker's TARGET test) and never ranked HP. Ally rows are offered only where the menu accepts them: a revive to a downed member, a cure (status mode2) to a member with one of the ailments in its mask, a restore to the member furthest below the maximum it restores (HP, or SP for a row whose only effect is an SP restore, `+0x14`, such as the SP items), an effect without HP or SP (a buff) to anyone. Up to `--jobs` continuations run at once, a new fork for each one that settles (each `fork` is resent until its pid or `fork_failed` marker appears, and a checkpoint that stops serving loses only its remaining candidates), and a beam of `--beam` checkpoints survives each depth, ranked by enemy HP lost, then party HP/SP fractions (capped at the maximum) and living members, less an expected loss of 80% of maximum HP per charged enemy for each living member (40% while guarding); `--guard-reserve` keeps that many of the best Guard nodes in the beam, and each `--phase-enemy ID` (a later form in the same battle) that has appeared on a path outranks any earlier form's HP. Enemy HP only ranks candidates, victory is the native terminal. A command the menu still refuses loops until `--step-timeout`; an actor's command on a given target refused at least twice and twice as often as accepted is no longer forked. When the walker fails a candidate because its bound target is absent from TARGET (a unit shielded by another, for one), the checkpoint's other candidates bound to that target are skipped and the command is not counted as refused. The search requires study admission: launched through `p4pc-run` with `P4PC_PRIORITY=study`, it forks nothing new while `$P4PC_ADMISSION_DIR/land-busy` exists (`--pause-file` names another file; only `--no-admission` runs without one), so a land check on the host takes the CPUs; running children finish, and `--max-seconds` excludes those pauses. The output is `OUT/tape.walk` (prefix, `battle:` line, one `battleturn:` line per fresh command), `nodes.jsonl` (every candidate's parent, line and status) and `search.json`; the files of candidates that fail, end without a win, repeat a kept state or leave the beam are deleted as the search goes. `--check-tape TAPE` instead runs a finished tape once in a fresh process without the fork (on a new worker build, say) and writes `OUT/check.json` with the native outcome. Without a win by `--max-depth` or `--max-seconds`, `search.json` `closest` names the best-ranked checkpoint ever kept (enemies, party, commands) and `closest.walk` is the tape that reaches it. After a win a fresh process runs `tape.walk` without the fork; `search.json` `witness` compares its trace, result, lockstep input log and per-frame states with the path's concatenated segments, excluding only the request-RAM SHA-256 field, which covers host heap pointers held in guest memory and so differs between processes.

## Engine seams and fidelity obligations

- Initial save-backed entry reuses the native party/enemy builders and sequence6 packet (`001932f0`, `00192e90`), not a reimplemented battle formula. Its entry kind is **harness-script6**: it does not execute an active event VM and is not claimed equivalent to the live-field constructor (`00174680`), which reuses existing field party units. Walker/PS2 witnesses must preserve their actual entry path rather than relabel this launcher.
- `00193840` retains the original loaded block byte counts in port-owned metadata, without changing the copy, alignment, guest data or RNG. Both the existing encounter harness and the simulator validate catalog bounds against that exact count and current published binding after all eight loads complete. Aligned arena gaps are not rows. Encounter enemy IDs must be below both the published enemy-bank extent and the native unit domain `p4_game_enemies_native_limit()` (`include/p4pc/game_enemies_native.h`, the `datUnitInit` `00231af0` bound): 0x150 for retail, the committed expanded catalog's limit otherwise. A relocated bank larger than that limit does not widen it.
- Native `00101350`/`kwlnRunFrame` provide the update boundary. The simulator is inactive in ordinary play; retained ordinary gates and inputs/reference hashes are unchanged.
- Renderless means a no-device rendering sink: no window, GL context, graphics submission/readback/present. CPU-side game draw callbacks, effect/motion/script work and RNG still execute; audio has the same deterministic completion clock. The initial sink supports only4:3 with an internal640x448 coordinate extent (`scale:1` or explicit`640x448`) and rejects other profiles. Logical target/viewport sizes remain available without a window, including the ordinary CPU projection/half-pixel path; that virtual extent is not a pixel image, and readback is a fatal unsupported operation. Offscreen GL or dropping only draw calls is not the renderless acceptance. A mod's authored images (`[resource-image]`) materialize here too: `p4gl_device_ready()` counts the open no-device backend as well as a current GL context (and neither once it closes), so the authored raster and its guest shadow are built and validated as with a device, while the upload and draws go to the sinks (`mod_resources_render_no_device`).
- Never poll enemy HP and declare victory. Retain native end/action/phase resolution, chained-encounter continuation, protagonist-death semantics and the committed terminal owner. Capture final resources before teardown loses their ownership.
- Fidelity compares exact authoritative state/RNG and the exact input schedule, first rendered-reference versus renderless, then actual ordinary save-to-fight runs, then PS2 lockstep witnesses. Different entry or decision timing is a different scenario, not permission to normalize differences.

The initial trace is deliberately scoped, not a full-RAM or complete-battle-state oracle: it retains every completed update's phase/flags/terminal, full party HP/SP/status, RNG draw count and hashes of the RNG image, context bytes`+0x0c..0x23`, each bounded unit's bytes`+0x98..0xab` and its0x30-byte native data record. Full RNG words are included at entry and terminal. FNV-1a64 detects regressions within that scope; it is not a cryptographic identity or proof about omitted action queues, script locals or private effect-RNG instances. The coordinator supplies SHA-256 input/artifact identities, and retained lockstep RAM/semantic witnesses provide the broader fidelity check.

## Native committed events (phase-2 integration)

`include/p4pc/battle_events.h` defines the C-only observation service, exercised within the scoped Windows native witnesses below, not a general retail/ABI qualification. The service has no Luau, package, mod-enable, allocation or RNG dependency. Eight native brokers can subscribe; a scripting runtime is one broker that fans out to its packages, not one native slot per script. Opaque registration tokens do not alias removed handles. Changes to subscriptions during synchronous delivery fail explicitly; callbacks may copy packets but not retain their addresses or mutate game state.

Native owners read the relevant interest bit before snapshots/payload construction. An unsubscribed owner makes no observer snapshots or packet copies. Actor packets copy the **64-bit** native action UID,32-bit unit UID, native identity and side; they expose no guest pointers.

Thin engine-body overrides include `p4pc/guest.h` for guest-address conversion, not the broader `gmem.h`: the latter also imports host string declarations into the game's renamed-CRT declaration scope. Keep collector prototypes from the actual native owner rather than adding a second block-scoped signature. Census changes must be reviewed against the exact added observer/picker code and qualified per ABI; no whole-baseline refresh or unsupported-rewrite suppression.

Injected overrides can contain includes after earlier native functions in the same generated translation unit. The narrow-return declaration pass anchors declarations before their first use, after an eligible earlier include, rather than after the last include anywhere in the file. This preserves the real `u16 btlPanelGetState` return type and prevents its earlier call from becoming an implicit `int` declaration on 32-bit builds. The action unit's `uiTask` field is a guest address: its mirror call explicitly converts it to the getter's native pointer parameter so the 64-bit address rewriter handles the boundary rather than leaving an implicit integer-to-pointer conversion.

- `001b15b0`: emit the actor actually admitted after native reorder/state dispatch/count/queue-flag commit, distinguishing ordinary versus active-followup queues. These are admitted opportunities, not invented uniform rounds.
- `001a4800`: emit the actual selected command after READY chooses its execution/presentation owner. Persona and Analyze are marked free; a committed attempt is not proof of a hit, paid cost or resolved outcome.
- `001f39d0`: reuse the already computed native HP/SP cost and actual item mutation. Copy resources/counts before and after; requested cost is distinct from net loss when native setters also clamp an over-maximum source. Do not calculate skill cost a second time to observe it.
- `001f3010`: copy finalized requested HP/SP/status/buff/result data and pre-mutation identities/resources, then publish after native status/death/endurance/reaction/gauge processing. Actual resource/status-application branches are explicit. Zero-delta packets are retained, not discarded as no-ops; a native clamp is not a new damage or SP-cost event.
- `001932f0`: a natural script request emits `P4_BATTLE_SCRIPT_REQUEST_BEGIN` synchronously before the original fade and parameter getter. `P4_BATTLE_SCRIPT_REQUEST_IDENTIFIED` emits the original getter's actual masked encounter ID immediately after that single call and before any party/enemy construction; `P4_BATTLE_SCRIPT_GROUP_CREATED` reports the actual created encounter-group guest address after its native assignment. A subscriber needing pre-fade state snapshots during BEGIN and associates the later ID with that pending request. None of these events alone proves task creation or a completed fight.
- `00174680`: `P4_BATTLE_FIELD_REQUEST_BEGIN` fires only when the existing task work's `+0x10c` request latch is zero and before the original state writes, free-object search or enemy allocation. The event is interest-gated and does not repeat the constructor or random decisions. It is a late pre-constructor observation, not the collision/advantage decision itself.
- `00192e90`: `P4_BATTLE_TASK_BEGIN` precedes `btlInit`; `P4_BATTLE_TASK_CREATED` follows the original constructor's task creation, setup copy and phase/ACTIVE initialization and carries its original returned guest task address. ## Native party policies and measurements (phase-2 integration)

The native C policies are exercised within the scoped Windows witnesses below. Policy1 is a greedy weakness exploiter,2 a cautious healer,3 a typical-player heuristic. They choose native Attack/Skill/Item/Guard commands from the real prepared command panel, currently using the selected persona. Named policies set the selected companions to native Direct Commands for the isolated run; tape policy0 preserves source tactics. Stable ties use command/skill/item identity and target UID. The controller has no damage-preview calls, enemy HP/stat reads, affinity reads or game-RNG draws. It knows its own party, inventory, native skill metadata and visible buffs/statuses. Weakness knowledge comes only from actual party-to-enemy damaging hit packets with native WEAK bit4, not CRITICAL bit2 or inferred neutral results from misses. The bounded ledger keys actual unit UID plus native identity; a tried attack is not an affinity discovery. Instant-kill outcomes do not teach a damage channel.

The policies read item rows through the native battle-item storage owner, including
the relocated list when a package adds item rows. Earlier screens with added
items could instead read the unused inline retail array and overlook consumables;
their outcomes must not be treated as equivalent policy evidence.

The corrected attentive-policy Knight refit (Hard, Physical Split and PARTY KIT
on, Golden off, typical-player L12 Izanagi, master seed
`48617264206d6f646520726573633072`, indices 0..399) won 213/400 at HP
×1.50 / St ×1.00, Wilson 95% 48.4–58.1%, median 13 items. The approved K4b
gear-off reference won 226/400, Wilson 51.6–61.3%. These are conditional bot
screens, not human first-attempt rates; the prior gear-on fit used stale IDs.

The greedy policy favors observed weaknesses and low-cost probes. The cautious policy prioritizes revival, cures and healing (protagonist below60%, allies below45%); the typical policy heals at45%/35%, retains an SP reserve and spends consumables less freely. Both prefer already observed opportunities. Nominal skill power is a heuristic input, never an alternate combat formula. Native target collectors decide legality, including the real different all-target status-filter path. The native menu and target handlers still commit commands, charge costs and execute combat. Unsupported command-panel/catalog layouts fail explicitly instead of silently reverting to another policy. Transport confirms auxiliary native prompts; it is not a second combat-decision policy.

The attentive policy (5, `attentive-player-v1`, scenario `{"kind":"attentive","version":1}`) plays like a careful player and uses only what the screen shows (`observed_damage_weakness_public_charge_guard`). It guards while any living enemy shows a charge (DatUnit `+0x14 & 0xC0000`, Power/Mind Charge) unless reviving or healing scores higher, heals the protagonist below 70% and allies below 50%, and does not spend a turn on a fixed heal of a quarter of the ally's HP or less unless that ally is at 25% or lower. It remembers per enemy the elements it saw weak, absorbed (HP rose) or nulled (no damage twice); a known absorber or null cancels its own share of a spread rather than vetoing it. It adds weight to the enemy the party damaged last and to any enemy seen healing its own side. It never switches Persona, so a scenario's entry state decides the protagonist's Persona.

The attentive Persona-ratings policy (6, `attentive-player-affinity-v1`, scenario `{"kind":"attentive-affinity","version":1,"ratings":{"path":P,"sha256":H}}`) is the attentive policy plus one Wild Card decision, for mod cohorts such as p4pc.skill-affinity. P is a ratings table (JSON `personas` `{"0x<id>": {category: rating}}` and `digest`, as `tests/mod_skill_affinity_test.py --ratings-out` writes it; private, since it derives from the user's disc) pinned by its file SHA-256. The coordinator compiles only `personas` into the ENTRY payload after the RNG block (+32 is its byte count, as for a walk plan): `P4AFFRT1`, a u32 count, then per Persona in ascending id a u16 id and one signed s8 rating (-128..127) per retail element in native order (phys, fire, ice, elec, wind, almighty, light, dark; a split table's phys is the best of slash/strike/pierce). The identity records the table, payload and table digests, and the result's `party_policy.ratings_sha256` must name the payload. At the protagonist's command, while Persona change is available (native kind5), the policy compares the stocked Personas of the native swap list: with a WEAK it has seen on a living enemy (retail elements 0..7 only; an expanded leaf is ignored), a Persona's value is its best rating among those elements, otherwise its best rating overall. It changes, through the native command wheel and swap list, only to a Persona whose value is strictly higher than the current one's (ties keep the current Persona, then the lowest row; an unlisted Persona never changes in), and then chooses the turn's command anew as the attentive policy would, against the new Persona's skills. Knowledge: `observed_damage_weakness_public_charge_guard_declared_persona_ratings`; the ratings are a declared table, not the game's hidden affinities.

The technical policy (7, `technical-player-v1`, scenario `{"kind":"technical","version":1}`) is the attentive policy plus Technical windows for hard mode's boss ailment windows (`observed_damage_weakness_public_charge_guard_ailment_landings`). It counts a Technical-set ailment (Rage, Fear, Silence, Panic; skill row +0x18 mode 1, mask at +0x1C) as attempted on an enemy where it commits the single-target choice, since an immune target may show no hit. It probes each such ailment at most twice per enemy and remembers an ailment it saw land (the hit's `added_status`, which the status icon shows). It prefers inflicting a known one on a target not already suffering it. Against a target showing an ailment it prefers the paired element (Fire/Rage, Ice/Fear, Elec/Silence, Wind/Panic) unless that element is already a known weakness. Like the other named policies it reads only public state; its win rates are relative comparisons.

The strategic candidate policy (8, `strategic-player-candidate-v1`, scenario `{"kind":"strategic","version":1}`, knowledge `observed_damage_weakness_public_charge_guard_ailment_landings_buff_state_fixed_heal_amounts_owned_persona_skills`) is an opt-in hypothesis, not a validated expert model and not a replacement for policies 1–7, whose behavior, names and evidence are unchanged. It is the technical policy (7) unchanged in its attentive and Technical reasoning — observed ailment landings, at most two probes per ailment and enemy, the paired-element preference — plus three conditional rules motivated by, not measured against, expert sources: the original PS2 boss guide on GameFAQs (buffs/debuffs, support targeting, charges), the PS2/PS3 Expert speedrun notes, and a Golden challenge run whose frames show a Persona change followed by Rakunda on the boss and an Amrita Soda cure (an edited, overleveled Golden run: it supports these as conditional legal tactics, not as PS2 calibration). Like policy 7 it does not read whether hard mode's Technical feature is enabled; without it the paired-element preference has no mechanical payoff. Its pure rules live in `include/p4pc/battle_strategy.h` (`src/platform/battle_sim/strategy.c`, `tests/battle_strategy_test.c`); `policy.c` feeds them only what a player sees or remembers:

- **Setup in a durable fight.** A buff mask that moves only in the party's favor (only raised `datCalcHasBuffMask` bits on a member, only lowered bits on an enemy) on a target not already holding it scores 1200 instead of 260/240, when every living enemy has already taken a party hit and survived and none has shown a weakness (no knockdown route is known, so the fight outlasts this turn). A boosted setup needs a party damage decision (Attack or a damaging skill/item) since the last committed setup; a heal or Guard does not reopen it, so setups never follow each other however many attacks came before. A held buff scores nothing, so it is re-cast only after it lapses: the held state stands for the cast and lapse a player sees and remembers (the Golden run's Rakunda description says 3 turns); whether PS2 P4 also draws enemy buff icons is unverified. The tempo and the change allowance below restart when the enemy units on the field share none with the previous decision's (a chained encounter's next wave).
- **Fixed heal amounts.** A heal on an ally below the attentive threshold whose amount is fixed (HP effect 5: the row's power is the HP restored, as the description says) loses the part of the ally's missing HP it leaves uncovered. Larger fixed heals therefore win, overheal earns nothing, and heals of unfixed amount keep the attentive score. In the Kanji seed-5 smoke run (strategic, update 7706) the hero at 57/329 under a visible charge used a 20-HP item (skill 288) while a 100-HP one (289) was held; if their rows are effect 5, as their exact 20/100 restorations in that trace suggest (not yet read from the rows), this rule chooses the 100-HP one. Every heal still outranks the charge Guard, as in the attentive policy.
- **Owned-Persona changes.** At the protagonist's command, after the current Persona's decision is scored, the policy scores each other stocked Persona's skills that its battle Skill list would show (btlSelectionRefreshList 00207140: nonzero DatPersonaRecord skills at `+0x0C` that are `p4_game_skill_active` with skill-table `flags01` bit 2) and whose cost the active Persona's pricing reports exactly. datCalcSkillCost (0023D9B0) halves an SP cost by Spell Master in the active Persona's list and derives HP and percentage costs from maximum HP/SP that Persona passives change, so only free skills and flat SP costs are scored, and those only while no skill cost stage is active and both Personas agree on Spell Master. When one beats the current best decision by more than 300 it changes (lowest row on ties) through the native wheel and swap list. That list (00202c60) has `datPersonaCountValidMembers()` rows whose row is the roster slot (`datPersonaRosterSlot(row)` at commit) and refuses the lead's row; an empty slot in that range is never chosen and a slot beyond it is not on the list, exactly as for policy 6. It changes at most once per command; the reopened panel decides with the new Persona's own menu.

Omitted rather than invented: a charge-time cure rule (whether the cured ally acts before the charged enemy needs a turn order the native queues do not establish, so cures keep the attentive 14000, below the charge Guard); Dekaja/Dekunda-style removal rows are not decoded (they keep the attentive score); a -kaja/-nda row whose `+0x20` mask is not direction-pure keeps the attentive score; a charge is answered only by Guard, and a heal on an ally below its threshold still outranks that Guard, as in policies 5 and 7; the Persona change prices no HP-cost or percentage-cost skill, compares stats only as the never-lower gate above (no stat-to-damage model), ignores maximum HP and the new Persona's own affinities against the enemy's attacks, and skips added skills outside the loaded catalog; a boss is recognized only through the durable-fight proxy. Its unit tests cover the decision rules, not combat; one synthetic smoke seed is not win-rate evidence.

An earlier native cohort (Windows nightly worker, synthetic Kanji Harder Golden/Physical Split entry, seeds 5–7) measured policy 5 winning 1/3, policy 7 2/3 and an earlier policy 8 0/3. Those runs selected the native menu's default target rather than the policy's chosen target, so they are not valid evidence of intended policy targeting. In all three policy-8 runs the protagonist changed from the level-25 lead to a level-15 or level-11 Persona and never changed back; the current stat gate (`p4_strategy_switch_stats`) refuses every change that entry's roster offers. With both the stat gate and selected-target fix, the same three seeds produced 2/3 wins for policy 5, 1/3 for policy 7 and 1/3 for policy 8. Three seeds do not establish balance, a policy ranking or expert-human play.

A victory is reported only at the native exit (phase17), after the result phase16 finishes its EXP and level-up flow. When a persona with eight skills levels up, that flow asks which skill to forget and its Yes/No defaults to No, so the periodic Cross re-selects forever: encounter517 (Shadow Teddie) with a Lv48 party stalled there to `update_limit` with `endState`1 already committed, not at a scripted boss end. For the named policies the session owns input while that prompt (`shdPersonaSkillSelectSeq`) reads it: it moves the list to the offered skill itself (slot8), confirms it and answers Yes, the native "did not learn" path. A known skill is never forgotten; if another row were chosen it answers No. Results report `result_prompt_capability` (`periodic_cross_native_skill_offer_decline_v1`, or `controller_tape` for tape policy0, whose tape must supply these inputs) and `result_prompts.skill_offers_declined`. Enemy HP is never polled to declare victory; runs that still reach `update_limit` stay censored.

Policy4 (`walk-battle-rules-v1`, scenario `{"kind":"walk","version":1,"plan":TEXT}`) runs a gate walk's battle driver: TEXT is `battle:`, `battlerule:` and `battleturn:` lines only (include/p4pc/walk_script.h; printable ASCII, at most 16384 bytes) and follows the RNG block in place of tape records. The worker parses it before launch, appends only the waits that keep the driver running until the battle task ends, steps `p4walk_frame` once per completed update and injects its mask; no field line, host clock, environment script or private RNG is involved. Like the named policies it sets Direct Commands. Its knowledge is the native unit records the battle rules read (`walker_battle_rules_native_unit_records`); `latency_updates` is echoed for the cohort check, while the plan's own `delay=` times its input. The result's `party_policy.plan_sha256` is the SHA-256 of TEXT, part of the cohort identity through the policy digest, so different plans never pool or share a replay ranking. A plan that fails (an absent bound ally, an over-long rule list or command tape) ends the run as `policy_error`/`walk_battle_plan_failed`. The session's skill-offer decline above runs before the walker for this policy too; the walker's driver confirms the other result messages and makes the same decline in real walks.

Native events define admissions, free commands, READY execution attempts, paid costs and finalized target packets separately. `turns.rounds` remains null: actor-specific native queues do not establish uniform rounds. `action_limit` is checked after a completed update, with a real native terminal taking precedence. Resource costs aggregate the native requested skill costs and actual item decrements. Native setter/clamp adjustments are separate from damage, recovery and expenditure. The report's explicit recovery scope excludes direct postbattle gift owners until those owners are instrumented; that partial counter is not a full-battle recovery claim.

`resources.initial_party` retains its `after_restore_before_constructor` boundary. Every result carries `table_catalog: {expanded, identity}` from `p4_game_table_catalog_identity` (`include/p4pc/game_table_extents.h`), retail included: `expanded:0` with the retail identity `SHA-256("p4pc-table-catalog-v1:retail")` (`e6474de9…a581`), or `expanded:1` with the content identity of the active expanded catalog. ### Declared mod cohorts (mod-witness, never retail)

A scenario may declare `mods: {packages: [{id, directory}], settings: {<id>: {<key>: <value>}}}`: 1..16 packages by manifest id, each directory's `mod.ini` declaring that id and a version, and settings only for declared packages (setting-key syntax, printable values without `#` or `;`). Only this declaration enables mods; ambient `P4PC_MOD_WITNESS`, `P4PC_MODS` or package environment is still refused or replaced. The coordinator hashes each package's regular files (links are refused), versions and the settings into one content identity, records it as `identity.mods`, copies the packages once into the batch's `mods/` (a resumed batch must find identical bytes), and writes each case profile's own `p4pc.ini` (`[mods] enabled=…`) and `mod-settings/<id>.ini`. Workers run with `P4PC_MOD_WITNESS=1`, `P4PC_MODS=1`, that `P4PC_MOD_DIR`, the profile's `P4PC_CONFIG` and `P4PC_BATTLE_SIM_MODS=<identity>`. The batch root is a mod-witness output root from the start, the report carries `run_mode:"mod-witness"` and `reference_eligible:false`, and the witness receipt tags every output except the staged packages.

Package identity uses `id` and `version` from the manifest's `[mod]` section;
a dependency's own `version` is not the package version.
On Windows, preparation and battle workers use `CREATE_NO_WINDOW` as well as
below-normal priority; their audio driver is dummy and rendered windows are hidden.

The worker accepts `P4PC_BATTLE_SIM_MODS` (lowercase SHA-256) only for battle simulation with `P4PC_MOD_WITNESS=1` and a `P4PC_MOD_DIR`; preparation and live mode refuse it, and without it `P4PC_MOD_WITNESS` is refused exactly as before. The loader then admits the declared packages through the ordinary optional-package boot (native recovery owner, game bindings, package boot, mods; content packs stay off), so any failure there ends a witness run instead of falling back to retail. A cohort hands the ENTRY image to the mods as the real load it stands for. The native reset in `datInitDefaultGameState` (`0x001113b0`) reports `"reset"` as at any load, then the exact image is staged through the save transport like a card read without metadata (`p4_mod_save_transport_loaded_untagged`; no sidecar, since an ENTRY carries no mod blocks), and the native `datSaveRestoreImage` (`0x0010e710`) proves, commits and announces it. A mod's save provider therefore sees `load(nil, "load")` before the encounter is constructed. Every result carries `mods`: `null` for retail, or `{identity, witness:true, active:[{id, version}]}` from the packages actually active; a cohort with none active fails as `engine_error`/`mod_set_unavailable`. The coordinator requires the declared identity and, outside native errors, the declared packages and versions, and refuses a retail result that names a mod set. `mods` is part of the measurement contract, so mod cohorts never pool or rank with retail runs or with another mod set.

A cohort of a `synthetic_lab` declarative entry may also declare `mods.equipment: [{actor, slot, item}]` (1..30 rows, actor 1..10, slot 0..2, one row per actor slot): added items, IDs from `P4_ITEM_RETAIL_COUNT` (1536) up, that exist only once the mod set is active. Preparation cannot equip them (it runs without mods, and an added item is never written into the save's three-halfword equipment fields), so the coordinator folds the rows into the cohort identity and passes them as `P4PC_BATTLE_SIM_EQUIPMENT=actor:slot:item,…`; the worker refuses them without a declared mod set. After the ENTRY image's load and before the party and encounter are built, it sets each row through `p4_game_tables_items_equipment_set` on the active item table, the expanded-equipment side state, which checks the row's kind/slot and the unit's compatibility bit; a refusal is `engine_error`/`mod_equipment_refused`, and a row no longer in place at the first protagonist command is `mod_equipment_lost_before_battle`. No stock changes: these are synthetic actors. RESULT `mods.equipment` echoes the rows and the coordinator requires them equal to the declaration. Retail equipment remains preparation's.

`p4mod test --scenario battle` ([p4mod](../modding/p4mod.md#battle)) is a second, single-run coordinator of the same contract for modders: one package (the mod under test), no settings or equipment, a `save` source given explicitly (a card slot's data file, checked against the same section/checksum rules before use), master seed 0 with `--seed` as the run index, and the identity computed exactly as `mod_cohort` does. It writes the `p4pc-run-mode.json` marker into its fresh work folder first, strips inherited `P4PC_*`/`SDL_*` variables, refuses an inherited `P4PC_MOD_WITNESS`, and requires the result's encounter, policy (and plan hash), identity and active package/version to match. It runs no admission, batches or statistics; its output is a single mod-witness run, never a reference.

The ENTRY stays numeric: the worker never sees a name. When `--encounter` is a formation key or a walk plan holds quoted skill/item/enemy names, `p4mod` first resolves them through the game's own catalog (`p4.data`, `data.catalog@1`) in a separate ordinary boot launch with the mod under test plus a private `p4mod.resolver` package, then writes the IDs into the plan it hashes and sends. Formations have keys but no names, so encounters are never looked up by name; party members remain native character IDs.

## Preparation wire v1 (native qualification scoped below)

Public party definitions remain JSON. The coordinator encodes the following bounded little-endian private request. The published layout itself is not evidence of a run; exercised native preparation receipts are scoped below. The native-only preparation command is:

```
EXE ELF --battle-prepare REQUEST --battle-prepared-image EFFECTIVE_SAVE --battle-prepare-result RECEIPT
```

Preparation runs once through the engine, outside the seed batch. A successful native `datSaveBuildImage` full-image export is frozen as the common battle source; the request and original source retain their identities and classification. No Python save editing or cloned save serializer is permitted. Source-attested means selected records/stock are attested to the unchanged source, not proof that an edited collection save is legally attainable. Synthetic grants remain labelled `synthetic_lab`.

The request begins with a160-byte header. All integers below are unsigned32-bit unless otherwise stated; unused/reserved fields must be zero. `FFFFFFFF` is the explicit preserve sentinel only where listed. Native validation rejects length/count/identity/reserved/mode errors before game mutation.

|8 | Header bytes:160 |
|12 | Flags:0 |

The exact payload order is source save bytes, actor records, persona records, inventory records, skill-decision records. There are no pointers, terminators, padding between regions, guest addresses or trailing bytes. Maximum request size is8MiB. Source save validation uses the same canonical native full/compact section rules as battle ENTRY. A source profile outside the supported plain party/equipment/stock model fails as a named capability, never an implicit approximation.

Each **actor record is64 bytes**: native ID@0; weapon/armour/accessory IDs@4/8/12 (`FFFFFFFF` preserves each); current-resource mode@16 (0 preserve,1 explicit HP/SP); HP/SP@20/24; native tactic@28 (`FFFFFFFF` preserve); bytes32–63 reserved zero. IDs are native IDs, not compact party-slot numbers. The record order declares the selected formation. Explicit HP/SP must respect native unit/death semantics; fill-living does not revive. Source gear selections must use attested ownership and actual native inventory/equipment transaction semantics; synthetic grants are never reclassified as acquired gear.

Each **persona record is112 bytes**: owner native ID@0; output hero roster slot@4 (companions use0); persona ID@8; mode@12 (0 preserve source record,1 synthetic exact record,2 native growth); source hero roster slot@16 (companions use0; native-init uses `FFFFFFFF`); target/asserted level@20 and EXP@24; growth origin@28 (0 source record,1 native init); eight starting skill IDs as16-bit integers@32; eight final/asserted skill IDs@48; five native stat bytes@64; five bonus-A bytes@69; five bonus-B bytes@74; reserved byte@79; first skill-decision index@80 and decision count@84; assertion/control mask@88; bytes92–111 reserved zero. Native empty skill is0, not `FFFF`. Mask bits1/2/4/8 assert level+EXP/final skills/stats/bonus bytes;16 explicitly replaces the starting skills for synthetic native-growth inputs. Unused value fields must zero. Source-preserve clones the actual selected record, with optional assertions; it does not reconstruct flags. Synthetic exact records use real native initialization and typed setters/copies, with consistent native EXP and zero bonus bytes. Native growth uses real progression, RNG, EXP curves and ordered learn/replacement operations; it must not assign the predicted final stats. Source-attested requests may not grant new records, stats, skills, stock or roster capacity.

Persona IDs are 1..65535 on the wire (the native record's 16-bit field); `FFFFFFFF` means no ID assertion and is valid only in preserve mode. The wire bound is schema-only. Native preparation checks generated and copied records against the active catalog: the ID must lie below the published persona-metadata extent (`0x7644c4`, 14-byte rows; 256 retail, the committed expanded catalog's otherwise), with a native level of 1..99. Added personas are therefore accepted only when their catalog is active, which simulator runs (mods off) never enable.

Preserve mode may omit the persona-ID assertion by encoding `FFFFFFFF` at+8; the actual resolved source ID must appear in the receipt. Synthetic-exact mode requires mask7 (level/EXP, final skills and stats), growth-origin1, source-slot `FFFFFFFF` and zero starting-skill/bonus bytes; optional mask bit8 asserts those zero bonus bytes. The native-init `FFFFFFFF` source-slot rule applies to companions too and takes precedence over their ordinary source-slot0 rule. Native growth with source origin uses an actual source record; native-init growth uses the same explicit sentinel. JSON decisions are nested per persona, and the encoder derives the flat first/count indices.

Each **inventory record is8 bytes**: native item ID@0, final declared count@4. Duplicate IDs fail. Inventory-mode1 defines exact battle-consumable quantities; unrelated stock survives. Native item kind, eligibility, stock capacity and quantity bounds are independently validated; a table header is not permission to expand persistent inventory. Source-attested counts cannot exceed attested source ownership.

Each **skill-decision record is24 bytes**: owner native ID@0; hero roster slot@4 (companions0); native reached level@8; actual newly learned skill@12; replacement slot0–7 or `FFFFFFFF` for native auto-add@16; expected removed skill@20 (0 for an empty slot). Decisions are ordered for their owning persona. A missing, extra, wrong-level, wrong-skill or stale replacement fails; no silent deterministic skill deletion is allowed.
